# 배송 명령 원장

공고별 포트폴리오 원칙에 따라 만든 **가상 최종 배송 백엔드 실습**입니다. 실제 카카오모빌리티 운영 시스템이나 내부 자료와 무관합니다. Java 표준 라이브러리만으로 주문·배송 명령의 일관성과 장애 후 복구를 검증합니다.

## 검증하는 문제

- 같은 명령을 다시 보내도 배송이 중복 생성되지 않는가
- 낙관적 버전 충돌과 잘못된 상태 전이를 차단하는가
- 배송 인원별 수용량을 지키고 취소 시 즉시 반환하는가
- 명령 결과와 감사 이벤트를 스냅샷·재시작 뒤에도 보존하는가
- 로컬 HTTP API가 정상·실패 응답을 구분하는가

## 핵심 설계

- 상태: `CREATED → ASSIGNED → PICKED_UP → COMPLETED`, 허용 상태에서 `CANCELLED`
- 명령 ID와 입력 내용 지문으로 멱등성 검사
- 배송 버전으로 낙관적 동시성 제어
- 배송 인원별 진행 중 배송 수 제한과 취소 시 수용량 반환
- 추가 전용 감사 이벤트 순서
- 임시 파일과 원자적 이동을 사용한 스냅샷, SHA-256 무결성 검사 후 복원
- JDK `HttpServer` 기반 읽기·쓰기 API

## 실행

JDK 21 이상이 필요합니다.

```powershell
.\verify.ps1
```

검증 스크립트는 본 코드와 테스트 코드를 새로 컴파일하고 정상·실패·복구·HTTP 경로 22개를 실행합니다. 스냅샷 본문 변조와 검사값 누락을 거부하는 경로가 포함됩니다.

## 범위와 한계

가상 자료로 백엔드 일관성 개념을 검증하는 개인 채용 준비 프로젝트입니다. 분산 합의, 실제 결제·배차 연동, 인증, 개인정보 처리, 운영 SLA를 구현했다고 주장하지 않습니다. 실서비스라면 지속 DB 트랜잭션, 발신함, 메시지 브로커, 인증, 요청량 제한과 관측 자료 내보내기를 추가해야 합니다.

## 구현 깊이와 검증

스냅샷이 명령별 최초 응답을 보존하도록 `COMMAND2` 레코드에 배송 상태·버전·배정 정보를 함께 기록합니다. 배송이 완료된 뒤 생성·배정 명령을 재시도해도 최신 상태로 바뀐 응답을 돌려주지 않습니다. 현재 배송 상태와 과거 명령 결과를 분리하고, 복원 시 결과 참조·이벤트 순서·배달원 용량을 검사합니다.

- **복잡도**: 배송 수를 `D`, 명령 수를 `M`, 이벤트 수를 `E`, 스냅샷 전체 바이트 수를 `B`라 두면 생성·배정·전이는 평균 `O(1)` 맵 조회·갱신입니다. 문자열 검증·지문 생성 비용은 해당 입력 길이에 비례합니다. 스냅샷 생성·복원은 `O(D + M + E + B)` 시간과 `O(D + M + E + B)` 공간이며, 직렬화·Base64·SHA-256·전체 파일 읽기를 포함합니다. 모든 명령은 모니터 잠금으로 직렬화되므로 대기 시간은 별도이며 병렬 처리량이 선형 증가한다고 주장하지 않습니다.
- **불변조건**: 동일 명령·동일 내용의 최초 응답은 재시작 후에도 같고 재실행으로 이벤트를 추가하지 않습니다. 배달원 활성 수는 수용량을 넘지 않으며 취소·완료 시 반환됩니다. 현재 상태의 버전보다 미래인 과거 명령 결과는 복원할 수 없습니다.
- **반례·동시성 검증**: [원장 테스트](src/test/java/lab/delivery/DeliveryCommandLedgerTest.java)는 생성→배정→수거→완료 뒤 저장·복원하고 생성·배정 재시도 응답과 현재 완료 상태를 각각 비교합니다. 수용량 3인 배달원에게 20개 스레드가 동시에 배정할 때 정확히 3건만 성공하는지, 복원 후 초과 배정이 거부되고 취소 후 한 자리가 반환되는지도 검사합니다.
- **한계**: 새 스냅샷은 최초 응답을 보존하지만 이전 `COMMAND` 형식에는 과거 응답 전체가 없어 현재 배송 상태를 연결하는 호환 경로를 유지합니다. 파일 시스템이 원자적 이동을 지원하지 않으면 일반 교체로 대체하므로 그 환경의 충돌·전원 장애 내구성을 보장하지 않습니다. 단일 JVM의 합성 배차이며 분산 배차·실서비스 SLA와 구분합니다.
