# 가상 이체 트랜잭션·발행 대기 복구 실습

이체가 DB에 반영됐는데 이벤트를 발행하지 못하거나, 소비자는 반영했는데 확인 응답이 유실되면 어떻게 복구해야 할까요? 이 실습은 **실제 로컬 SQLite 트랜잭션**에 가상 계좌의 출금·입금, 양쪽 기장과 outbox를 함께 기록하고, 별도 소비자 DB의 inbox로 중복 반영을 막습니다.

## 실행

Python 3.11 이상, 표준 라이브러리만 필요합니다. 저장소 루트에서 실행합니다.

```powershell
python -B ai/transactional-outbox-recovery-lab/ledger.py
python -B -m unittest discover -s ai/transactional-outbox-recovery-lab/tests -v
```

데모는 출금 갱신 뒤 오류를 주입해 원래 잔액으로 되돌아가는지 확인합니다. 재시도 후 소비자는 한 번 반영하고 ACK 손실 이후 동일 이벤트를 다시 받아도 추가 반영하지 않습니다. 기본 실행은 메모리 DB만 사용합니다.

## 구현 판단

- `BEGIN IMMEDIATE`로 한 SQLite 쓰기 트랜잭션을 시작하고 잔액·기장·발행 대기 기록을 함께 커밋합니다. 출금 뒤, 기장 뒤, 커밋 직전의 합성 오류에는 모두 롤백합니다.
- 동일 이체 ID와 같은 내용은 기존 커밋 결과를 반환합니다. 같은 ID의 다른 내용은 거부하며 정수 원화, 잔액 부족과 정수 범위 초과를 검사합니다.
- 발행자는 소비자 커밋 이후 ACK를 기록합니다. 소비자는 이벤트 ID와 본문을 함께 저장하고 projection 반영을 같은 트랜잭션으로 수행합니다. ACK 손실 시 재전달되지만 잔액 증감은 중복 반영하지 않습니다.
- 실패 테스트는 Python 함수의 반환값뿐 아니라 실제 DB 잔액·기장·outbox·inbox를 조회합니다. 파일 DB를 닫고 다시 연결한 후 동일 명령을 재시도하는 검증도 포함합니다.

## 관측 범위와 한계

Conda Python에서 기존 이체 기장 검사 10개와 신규 복구 실습 10개 검사를 실행했습니다. 기존 자료는 첫 실패 이후의 불확실한 잔액으로 후속 거래를 재생하지 않도록 개선했습니다.

계좌·금액은 모두 합성입니다. 실제 은행 시스템, 고객 데이터, 네트워크 메시지 브로커에는 연결하지 않습니다. SQLite의 단일 쓰기 잠금을 활용한 예이며 대규모 분산 시스템의 동시성·프로세스 강제 종료·디스크 손실·정산 정책을 검증하지 않습니다. 발행 순서와 보관 주기, 이벤트 스키마 진화, 계좌 권한·감사 정책은 실서비스 적용 전 별도 설계가 필요합니다. AI 보조로 작성한 공개 실습을 과거 회사의 실무 구현으로 주장하지 않습니다.
